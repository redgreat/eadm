## 核心实体表结构设计

### 用户表 (eadm_user)

用户表 `eadm_user` 是系统权限管理的基础，存储了所有用户的核心信息。

- **字段设计与语义**:
  - `Id` (CHAR(12)): 自定义主键，前缀为 "EU"，用于唯一标识用户。
  - `TenantId` (CHAR(12)): 外键，关联 `eadm_tenant` 表的 `Id`，标识用户所属租户。
  - `LoginName` (VARCHAR): 用户登录名，具有唯一性约束，是用户登录系统的凭证。
  - `UserName` (VARCHAR): 用户真实姓名。
  - `Email` (VARCHAR): 用户联系邮箱。
  - `CryptoGram`/`Passwd` (VARCHAR): 存储加密后的用户密码。
  - `UserStatus` (TINYINT/SMALLINT): 用户状态码，`0` 表示启用，`1` 表示禁用。该字段用于逻辑控制用户登录权限。

- **约束与索引**:
  - **主键**: `Id` 字段为主键。
  - **外键**: `TenantId` 字段引用 `eadm_tenant(Id)`，确保用户必须归属于一个有效的租户。
  - **唯一性**: `LoginName` 字段具有唯一索引，防止重复注册。
  - **索引**: 为 `TenantId` 和 `UpdatedAt` 字段创建索引，以优化按租户查询和按更新时间排序的性能。

### 角色表 (eadm_role)

角色表 `eadm_role` 用于定义系统中的权限角色，实现基于角色的访问控制（RBAC）。

- **字段设计与语义**:
  - `Id` (CHAR(12)): 自定义主键，前缀为 "ER"，用于唯一标识角色。
  - `RoleName` (VARCHAR): 角色名称，如“超级管理员”、“注册租户”。
  - `RolePermission` (JSON/CLOB): 存储角色的权限配置，以 JSON 格式保存，定义了该角色对各个功能模块（如健康、财务、定时任务）的访问权限。
  - `RoleStatus` (TINYINT/SMALLINT): 角色状态码，`0` 表示启用，`1` 表示禁用。禁用的角色将无法被分配给新用户。

- **约束与索引**:
  - **主键**: `Id` 字段为主键。
  - **唯一性**: `RoleName` 字段具有唯一索引，确保角色名称不重复。
  - **索引**: 为 `RoleStatus` 字段创建索引，便于快速筛选启用或禁用的角色。

### 设备表 (eadm_device)

设备表 `eadm_device` 用于管理物理设备，如充电宝、手表等。

- **字段设计与语义**:
  - `DeviceNo`/`Id` (VARCHAR/CHAR(12)): 主键。在 Kingbase、PostgreSQL、DB2 和 Oracle 版本中，`DeviceNo` 是主键（VARCHAR 类型）。而在 MySQL 和 TiDB 版本中，使用 `Id` (CHAR(12)) 作为自定义主键，`DeviceNo` 作为普通字段。
  - `Imei` (VARCHAR): 设备的 IMEI 号，用于唯一标识移动设备。
  - `SimNo` (VARCHAR): SIM 卡号。
  - `Enable`/`Deleted` (BOOLEAN/TINYINT): 设备在线标志。在 Kingbase、PostgreSQL、DB2 和 Oracle 中，`Enable` (BOOLEAN) 为 `true` 表示设备启用（在线）。在 MySQL 和 TiDB 中，使用 `Deleted` (TINYINT) 字段，`0` 表示未删除（在线），`1` 表示已删除（离线）。
  - `Remark` (VARCHAR): 设备描述信息。

- **约束与索引**:
  - **主键**: 根据数据库版本，主键为 `DeviceNo` 或 `Id`。
  - **索引**: 为 `SimNo` 字段创建索引，便于通过 SIM 卡号快速查找设备。

### 财务记录表 (fn_paybilldetail)

财务记录表 `fn_paybilldetail` 用于存储详细的财务流水信息。

- **字段设计与语义**:
  - `Id` (INT/BIGINT): 自增主键。
  - `Sourcetype` (INT/SMALLINT): 财务流水来源类型，通过注释定义：`1` 为支付宝，`2` 为微信，`3` 为青岛银行，`4` 为中国银行。
  - `Inorout` (VARCHAR): 标识交易是收入（收）还是支出（支）。
  - `Amount` (NUMERIC/DECIMAL): 交易金额，使用高精度的 `NUMERIC(18,2)` 类型，确保财务计算的准确性。
  - `Paystatus` (VARCHAR): 交易状态，如“成功”、“失败”、“处理中”。
  - `Tradetype` (VARCHAR): 交易分类，如“转账”、“消费”、“退款”。
  - `Tradetime` (TIMESTAMP/TIMESTAMPTZ/DATETIME): 交易发生的时间。

- **约束与索引**:
  - **主键**: `Id` 字段为主键。
  - **索引**: 为 `Sourcetype`, `Inorout`, `Paymethod`, `Paystatus`, `Tradetype`, `Tradetime` 等常用查询条件字段创建索引，以优化财务报表的查询性能。

### 定时任务表 (eadm_crontab)

定时任务表 `eadm_crontab` 用于管理系统中需要周期性执行的任务。

- **字段设计与语义**:
  - `Id` (BIGINT/CHAR(12)): 主键。在 MySQL 和 TiDB 中为 `BIGINT AUTO_INCREMENT`。在 Kingbase、PostgreSQL、DB2 和 Oracle 中为 `CHAR(12)`，前缀为 "CR"，通过序列和触发器生成。
  - `CronName` (VARCHAR): 任务的名称，便于识别。
  - `CronExp` (VARCHAR): 定时表达式（Cron Expression），定义任务的执行周期。
  - `CronMFA` (VARCHAR): 任务备注或描述。
  - `StartDateTime`/`StartTime`: 任务的开始执行时间。
  - `EndDateTime`/`EndTime`: 任务的结束执行时间。
  - `CronStatus` (TINYINT/SMALLINT): 任务状态码，`0` 表示启用，`1` 表示禁用。

- **约束与索引**:
  - **主键**: `Id` 字段为主键。
  - **索引**: 为 `CronName` 字段创建索引，便于通过名称快速查找任务。

## 跨数据库语法差异与兼容性处理

为支持多种数据库，`DataStruct.sql` 脚本针对不同数据库的语法特性进行了适配。

- **数据类型差异**:
  - **字符串类型**: MySQL 和 TiDB 使用 `VARCHAR` 和 `TEXT`。Oracle 使用 `VARCHAR2`。Kingbase、PostgreSQL、DB2 和 Oracle 使用 `CLOB` 存储 JSON 权限数据，而 MySQL 和 TiDB 直接使用 `JSON` 类型。
  - **布尔类型**: Kingbase、PostgreSQL 和 DB2 使用原生的 `BOOLEAN` 类型。MySQL 使用 `TINYINT(1)` 模拟布尔值。Oracle 使用 `INTEGER` (0/1)。
  - **时间类型**: MySQL 使用 `DATETIME`。PostgreSQL、Kingbase 使用 `TIMESTAMPTZ` (带时区的时间戳)。Oracle 使用 `TIMESTAMP WITH LOCAL TIME ZONE`。DB2 使用 `TIMESTAMP`。

- **主键与自增机制**:
  - **MySQL/TiDB**: 使用 `AUTO_INCREMENT` 关键字实现自增主键。
  - **PostgreSQL/Kingbase**: 使用 `SERIAL` 类型或 `GENERATED ALWAYS AS IDENTITY`。
  - **DB2/Oracle**: 使用 `GENERATED ALWAYS AS IDENTITY`。
  - **自定义主键 (EU, ER, ED)**: 对于需要特定前缀的主键（如 "EU"），MySQL 和 TiDB 使用自定义函数 `fn_nextval`。其他数据库则通过创建序列（`SEQUENCE`）并结合触发器（`TRIGGER`）在插入数据前生成主键值。

- **函数与触发器**:
  - **更新时间**: MySQL 使用 `ON UPDATE CURRENT_TIMESTAMP`。其他数据库则通过创建触发器，在 `UPDATE` 操作时自动更新 `UpdatedAt` 字段。
  - **序列**: Kingbase、PostgreSQL、DB2、Oracle 使用 `CREATE SEQUENCE`。MySQL 不支持序列，因此使用 `sys_sequence` 表和 `fn_nextval` 函数来模拟。

## 建表顺序与依赖关系

由于表之间存在外键依赖，必须遵循正确的建表顺序，否则会因引用的父表不存在而建表失败。

1.  **基础表**:
    - `sys_dict`: 系统字典表，作为其他表的参考数据。
    - `eadm_tenant`: 租户信息表，是 `eadm_user` 的父表。

2.  **核心实体表**:
    - `eadm_user`: 用户表，依赖 `eadm_tenant`。
    - `eadm_role`: 角色表，独立存在。
    - `eadm_device`: 设备表，独立存在。

3.  **关联表**:
    - `eadm_userrole`: 用户角色关联表，依赖 `eadm_user` 和 `eadm_role`。
    - `eadm_userdevice`: 用户设备关联表，依赖 `eadm_user` 和 `eadm_device`。

4.  **业务数据表**:
    - `fn_paybilldetail`: 财务记录表。
    - `eadm_crontab`: 定时任务表。
    - 其他业务数据表（如 `lc_watchdaily`, `lc_carlocdaily`）。

## 常见建表问题与解决方案

在执行 `DataStruct.sql` 脚本时，可能会遇到以下问题：

- **字符集不匹配**:
  - **问题**: 数据库或表的字符集（如 `utf8mb4`）与脚本期望的不一致，可能导致中文乱码或插入失败。
  - **解决方案**: 在建表前，确保数据库的默认字符集和排序规则正确。可以使用 `ALTER DATABASE` 语句修改，或在 `CREATE TABLE` 语句中显式指定 `CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci`。

- **权限不足**:
  - **问题**: 执行脚本的数据库用户缺少 `CREATE`, `DROP`, `ALTER` 等 DDL 权限，导致建表或删表操作被拒绝。
  - **解决方案**: 联系数据库管理员，为执行脚本的用户授予足够的权限，例如 `GRANT ALL PRIVILEGES ON eadm.* TO 'user_eadm'@'%'`。

- **对象已存在**:
  - **问题**: 脚本中使用了 `DROP TABLE IF EXISTS`，但如果用户没有 `DROP` 权限，或者在某些严格模式下，仍可能报错。
  - **解决方案**: 确保用户有 `DROP` 权限。或者，在执行脚本前手动清理旧的数据库对象。

- **序列/触发器创建失败**:
  - **问题**: 在 Kingbase、PostgreSQL 等数据库中，如果序列或触发器已存在，`CREATE SEQUENCE` 或 `CREATE OR REPLACE TRIGGER` 可能会失败。
  - **解决方案**: 脚本中使用了 `DROP SEQUENCE IF EXISTS` 和 `CREATE OR REPLACE TRIGGER` 来确保操作的幂等性。确保执行用户有操作序列和触发器的权限。
